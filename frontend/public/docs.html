UK Wind & Procurement Dashboard

Full-stack application for analysing wind generation forecast accuracy and day-ahead procurement gap — built on live Elexon BMRS data.

FastAPI React 18 TypeScript Elexon BMRS Recharts Tailwind CSS Docker

Introduction

This dashboard helps electricity market participants understand two related questions:

  1. How accurate are the published wind generation forecasts? — Measured as MAE, RMSE, bias and WAPE by lead-time bucket.
  2. How much power did we still need to procure after our day-ahead decision? — The "procurement gap": the difference between what the forecasts implied we needed to buy versus what we actually needed.

All data is pulled live from Elexon BMRS (the British National Grid's official settlement data service) at the moment you click Fetch Data. No data is stored server-side between requests beyond a short in-memory cache.

ℹ️

No API key required. Elexon BMRS is a public API. The app works immediately after startup with no registration or credentials.

Data Flow

Every request follows the same pipeline from browser click to rendered chart:

  1. User selects a decision date and cutoff time (e.g. 28 Oct 2026, 10:00 UTC) and clicks Fetch Data.
  2. The React frontend calls GET /api/analysis or /api/procurement.
  3. The FastAPI backend fetches 3 days of WINDFOR forecasts published up to the cutoff from Elexon. Results are cached in memory (5 min for recent data, 1 hr for historical).
  4. The select_latest_forecasts() function picks, for each delivery hour, the most recently published forecast whose publishTime ≤ cutoff. Only periods after the cutoff are kept (forward-looking).
  5. FUELHH actuals are fetched for the delivery window and averaged from half-hourly → hourly to match the forecast granularity.
  6. Errors, metrics, lead-time buckets, and coverage are computed. For procurement, NDF demand forecasts and actual demand (FUELHH all-fuels sum) are added to the pipeline.
  7. A typed JSON response is returned and rendered into charts, metric cards, and tables.

Elexon BMRS

Base URL: https://data.elexon.co.uk/bmrs/api/v1

All three datasets use the /stream endpoint variant, which returns a flat JSON array rather than a paginated envelope. Requests use two query parameters to filter by publish time:

ParameterFormatExample
publishDateTimeFromISO 8601 UTC2026-10-25T10:00:00Z
publishDateTimeToISO 8601 UTC2026-10-28T10:00:00Z
formatstringjson
⚠️

The backend always requests the 3 days before the cutoff for forecasts. This is because WINDFOR publishes forecasts up to 14 days ahead — the 3-day window captures all relevant forecast vintages for same-day and next-day delivery.

WINDFOR

Wind generation forecast dataset. Published approximately every 30 minutes by National Grid ESO and distributed via Elexon BMRS.

FieldTypeDescription
startTimeISO datetimeStart of the delivery hour (UTC)
publishTimeISO datetimeWhen this forecast version was published
generationfloatForecast wind generation in MW

Granularity: hourly. Multiple publishTime values exist per startTime — each is a different forecast vintage (run). The app selects the latest vintage published before the decision cutoff.

FUELHH

Half-hourly actual generation by fuel type. Used in two ways:

  • Wind actuals: filtered to fuelType=WIND
  • Total demand actuals: all fuel types summed per period. Since the grid is always in balance, total generation = total consumption.
FieldTypeDescription
startTimeISO datetimeStart of the 30-min settlement period
fuelTypestringe.g. WIND, GAS, NUCLEAR, COAL, SOLAR…
generationfloatActual generation in MW

Granularity: half-hourly. Two 30-min periods are averaged to produce one hourly bucket matching WINDFOR.

NDF (National Demand Forecast)

National Grid ESO's published forecast of total UK electricity demand. Used in the procurement gap analysis as the demand side of the residual calculation.

FieldTypeDescription
startTimeISO datetimeStart of the 30-min period
publishTimeISO datetimeWhen this forecast version was published
demandfloatForecast demand in MW
boundarystringOnly N (National) records are used

Granularity: half-hourly. Same averaging to hourly applied as FUELHH. Same latest-before-cutoff selection logic as WINDFOR.

Forecast Selection

For any given delivery hour, there are many published forecast vintages. The app picks the one a market participant would have seen at their decision time.

Algorithm

# 1. Filter: only forecasts published on or before the cutoff
eligible = [f for f in forecasts if f["publishTime"] <= cutoff_dt]

# 2. For each delivery startTime, pick the maximum publishTime
best = {}
for record in eligible:
    key = record["startTime"]
    if key not in best or record["publishTime"] > best[key]["publishTime"]:
        best[key] = record

# 3. Keep only forward-looking periods (delivery AFTER the cutoff)
selected = {k: v for k, v in best.items() if k > cutoff_dt}
✅

Why forward-looking only? The cutoff is the moment the day-ahead decision is made. Delivery periods before the cutoff have already passed and are irrelevant to the procurement decision.

Lead Hours

Each delivery period is assigned a lead time: how far ahead the forecast is looking from the decision cutoff.

lead_hours = (delivery_time - cutoff_dt).total_seconds() / 3600

Lead hours drive the Lead-Time Breakdown chart, which shows how accuracy degrades with time horizon.

BucketRangeTypical context
0–24 h0 ≤ lead < 24Same-day / next-day delivery
24–48 h24 ≤ lead < 48Day-ahead market delivery
48–72 h48 ≤ lead < 72Two-day forward
72 h+≥ 72Long-range, higher uncertainty

Granularity Mismatch

WINDFOR is published in hourly buckets. FUELHH and NDF are half-hourly. To compare them, all half-hourly series are averaged into hourly buckets.

# Group half-hourly records by their :00 hour key
buckets = {}
for rec in actuals:
    hour_key = rec["startTime"].replace(minute=0, second=0, microsecond=0)
    buckets.setdefault(hour_key, []).append(rec["generation"])

# Average the two 30-min values per hour
hourly = {k: sum(v) / len(v) for k, v in buckets.items()}
ℹ️

Why average? WINDFOR reports an average MW rate for each hour. FUELHH also reports average MW for each 30-min period. Averaging two half-hours preserves the MW scale — no unit conversion required.

Accuracy Metrics

All metrics are computed only over periods where both a forecast and an actual are available (matched periods).

MAE
Σ|forecast − actual| / n

Mean Absolute Error. Average magnitude of forecast error in MW. The primary headline metric.

RMSE
√(Σ(forecast − actual)² / n)

Root Mean Square Error. Penalises large errors more than MAE. Always ≥ MAE.

Bias
Σ(forecast − actual) / n

Signed average error. Positive = systematic over-forecast. Negative = under-forecast.

WAPE
Σ|error| / Σ|actual| × 100

Weighted Absolute Percentage Error. Scale-free. Avoids division-by-zero at low generation.

Coverage

Not every delivery period will have an actual available (actuals are published after real-time). Coverage is reported as a percentage.

coverage_pct = matched_periods / total_forecast_periods × 100

If coverage falls below 80%, a warning banner is shown on the Wind Accuracy tab.

Capacity Factor

capacity_factor = avg(actual_MW) / 30_000 × 100  # assumes 30 GW installed

Procurement Gap Analysis

The core business question: a market participant buys electricity from the day-ahead market to serve their consumers. Wind generation reduces how much they need to buy. How wrong was their procurement plan?

Forecasted procurement need

= Demand forecast − Wind forecast

What the market said: buy this much from other sources.

Actual procurement need

= Actual demand − Actual wind

What really happened: this much power came from non-wind sources.

Procurement gap error

= Forecasted need − Actual need

+ = over-bought (wasted cost). − = under-bought (must top-up at balancing market).

Under-bought vs Over-bought

Gap signMeaningCommercial consequence
Negative (−) Under-bought — you purchased less than you needed Must buy the shortfall on the balancing / intraday market, typically at a price premium
Positive (+) Over-bought — you purchased more than you needed Surplus capacity: either sold back or written off as wasted cost
💡

The total under-bought volume (sum of all negative gap periods) is the most actionable number — it tells you exactly how many MW·h you would have needed to source from the balancing market on that day.

Demand Actuals Derivation

Elexon does not publish a dedicated "actual demand" endpoint. Instead, the app sums all fuel types from FUELHH per period:

# Gas + Nuclear + Wind + Solar + Hydro + Imports + ... = Total demand
totals = {}
for item in fuelhh_all_fuels:
    t = parse_dt(item["startTime"])
    totals[t] = totals.get(t, 0.0) + float(item["generation"])

This works because the grid is always in balance: total metered generation ≡ total consumption at every settlement period.

Multi-day accuracy trend. Runs _analyse() in parallel for each day using asyncio.gather.

ParamRequiredDefaultDescription

end_dateYes—YYYY-MM-DD. Max 30 days range.

Caching & Retry

In-memory TTL cache

Every Elexon HTTP response is cached in a process-level dict keyed by a SHA-256 of the URL + params. Cache hit avoids re-fetching on repeated identical requests (e.g. switching dashboard tabs).

Data ageTTLRationale
Last 48 hours (recent)5 minutes (CACHE_TTL_SECONDS)Actuals may still be arriving; keep fresh
Older than 48 hours1 hour (CACHE_TTL_HISTORICAL)Historical data is immutable; cache aggressively

Retry with exponential backoff

Every Elexon call retries up to MAX_RETRIES times (default 3) on network errors and HTTP 5xx responses. 4xx errors are not retried.

attempt 1  → immediately
attempt 2  → wait 1s
attempt 3  → wait 2s
→ raises RuntimeError if all attempts fail

Business & Analytical Gaps

These are the gaps that most directly affect the correctness and commercial usefulness of the current analysis, ordered by priority.

Priority 1 — Critical

Solar Generation

Solar is the second-largest renewable in GB. On a summer day it can contribute 8,000–10,000 MW, dramatically reducing residual demand. The current procurement gap analysis ignores solar entirely, which means residual demand calculations are materially wrong during daylight hours in spring and summer.

What needs to be added

  • Solar forecast: Sheffield Solar API — publishes GB-wide solar generation forecasts, updated every 30 min, free for non-commercial use.
  • Solar actuals: Already in FUELHH as fuelType=SOLAR — same pipeline as wind actuals.
  • Combined residual: Residual demand = Demand forecast − Wind forecast − Solar forecast. This fixes the procurement gap numbers.

Updated forecasted need

= Demand fcst − Wind fcst − Solar fcst

Updated actual need

= Actual demand − Actual wind − Actual solar
Priority 2 — Critical

Price Impact of Procurement Gap (£ Cost)

The dashboard tells you how many MW you were wrong by, but the real business KPI is what it cost. Elexon publishes imbalance prices every settlement period — the System Buy Price (SBP) when the system is short and the System Sell Price (SSP) when long. Without prices, a 500 MW shortfall at £50/MWh looks identical to a 500 MW shortfall at £1,200/MWh (a real balancing market spike).

Datasets to add

Elexon DatasetWhat it providesUnit
ISPSTACKImbalance Settlement Prices — SBP & SSP per period£/MWh
SYSDEMSystem demand — cross-check for actual demandMW

New metrics this enables

  • Cost of under-buying: Shortfall MW·h × SBP = £ paid on balancing market
  • Cost of over-buying: Surplus MW·h × (DA price − SSP) = £ wasted or lost on sell-back
  • Total daily procurement cost error: The single most actionable number for a trading desk
Priority 3 — High Value

Intraday Forecast Comparison (Multiple Cutoff Times)

Traders do not make one decision per day — they continuously re-position as better forecasts become available throughout the day. Currently the app lets you pick one cutoff. A comparison mode across multiple cutoffs (e.g. Day-1 17:00, Day-0 08:00, Day-0 12:00, Gate Closure 1 h ahead) would show precisely when accuracy improves enough to justify re-trading, and what the expected cost saving is.

What the feature would show

  • Side-by-side MAE at D-1, D-0 08:00, D-0 12:00, gate closure
  • MW improvement per re-forecast — is it worth the trading cost?
  • Which hours benefit most from later forecasts (e.g. peak demand periods)
Priority 4 — High Value

Demand Forecast Accuracy (NDF vs Actual)

The procurement gap is driven by two forecasts — wind and demand. The current dashboard only breaks out wind forecast error. NDF accuracy (demand forecast vs actual demand) is never shown separately. On days with high demand volatility (cold snaps, heatwaves, bank holidays), NDF error can exceed wind error and become the dominant driver of procurement gap.

New metrics this enables

  • NDF MAE / bias vs wind forecast MAE / bias — which is worse?
  • Procurement gap decomposition: % attributable to wind error vs demand error
  • Worst demand forecast days — useful for identifying high-risk procurement periods
Priority 5 — Medium Value

Seasonal & Monthly Breakdown

Wind accuracy and capacity factor vary dramatically across seasons. Winter brings higher wind output but also more volatile weather. Summer has lower wind but higher solar. Monthly or seasonal analysis would let users identify the highest-risk procurement periods across the year and set appropriate risk margins.

What this would show

  • Average MAE by month / season over multiple years
  • Monthly capacity factor distribution (box plots)
  • Which months have highest procurement gap variance — risk calendar
  • Year-on-year comparison as installed capacity grows

Technical Gaps

Infrastructure and code quality improvements needed before the application is used in a production trading environment.

CSV / Excel Export

No way to download the period table or procurement gap data. Traders need raw numbers for their own offline models and reports. Should export all columns visible in the current table.

Backend: GET /api/analysis/export?format=csv
Frontend: download button per table
Authentication & Access Control

The app is currently fully open — anyone with the URL can use it. For a commercial tool, at minimum an API key or OAuth login should gate access. Role-based access could restrict who can see price data vs accuracy data.

Options: API key header, OAuth2 / JWT, Clerk/Auth0
Rate Limiting

The /api/trend endpoint fires up to 30 parallel Elexon requests. No throttle exists. A single user or a misconfigured client could exhaust the backend or hit Elexon rate limits, causing 429 errors for everyone.

Add: slowapi / fastapi-limiter per IP + per endpoint
Unit & Integration Tests

Zero tests exist. The forecast selection algorithm, metric calculations, and procurement gap formulas all need test coverage. A single off-by-one in lead-hours or an incorrect averaging step could silently produce wrong numbers.

pytest for backend · Vitest for frontend calculations
Comparison Mode

No side-by-side view of two dates, two cutoff times, or two forecast providers. This is the most requested feature for forecast benchmarking — showing whether a different decision cutoff would have resulted in a better procurement outcome.

UI: split-panel with two independent date pickers

Used for running iterative development sessions, debugging backend errors, production hardening (retry logic, caching, Docker non-root setup), and generating this documentation page.

Development Workflow

Phase 1 — Research

ChatGPT & Gemini used to understand UK electricity market mechanics, Elexon API structure, procurement gap methodology, and accuracy metrics used in industry.

Phase 2 — Architecture

Claude Code designed the full project structure — FastAPI + React + Docker stack, service layer breakdown, Pydantic schemas, and API contract.

Phase 3 — Implementation

All backend services, React components, Recharts visualisations, Tailwind styling, and Docker configuration written iteratively with Claude Code in VS Code.

Phase 4 — Production

Production hardening (retry, caching, non-root Docker, health checks, security headers, error boundaries) and full documentation generated with Claude Code.

ℹ️

This project demonstrates an AI-assisted development workflow where LLMs handle both the knowledge work (research, architecture decisions) and the implementation work (writing and debugging every line of code), with a human directing the product vision and requirements throughout.

Glossary

TermDefinition
BMRSBalancing Mechanism Reporting Service — Elexon's public data API for the UK electricity market.
WINDFORWind generation forecast dataset. Published every ~30 min by National Grid ESO.
FUELHHHalf-hourly actual generation by fuel type. Published after each settlement period.
NDFNational Demand Forecast. Half-hourly demand forecast published by National Grid ESO.
Cutoff timeThe moment the day-ahead procurement decision is made. Only forecasts published before this time are used.
Lead hoursTime from the cutoff to the delivery period. Longer lead = less accurate forecast.
Residual demandTotal demand minus wind generation = power that must come from other sources (gas, nuclear, imports, etc.).
Procurement gapForecasted residual − actual residual. Positive = over-bought. Negative = under-bought.
Balancing marketThe near-real-time market where shortfalls are topped up, usually at a price premium to the day-ahead market.
Settlement periodA 30-minute interval in the UK electricity market. 48 periods per day.
Forecast vintageA specific publishTime of a forecast. Multiple vintages exist per delivery period.
MAEMean Absolute Error in MW.
RMSERoot Mean Square Error in MW. Penalises large errors more than MAE.
WAPEWeighted Absolute Percentage Error. Scale-free accuracy metric.
Capacity factorAverage actual wind generation as a percentage of assumed installed capacity (30 GW).
